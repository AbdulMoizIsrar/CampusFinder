# ADR-001: Adopt a layered modular monolith

**Status:** Accepted  
**Context:** CSC337 Lab 01–06 CampusFinder, mid-term, Fall 2026

## Problem
The portal is expected to serve a campus-level user base (hundreds of users rather than millions). It must deliver authenticated REST CRUD, a read-only GraphQL dashboard, private Socket.IO events and a controlled claims workflow within a single student project. Splitting these features into microservices adds deployment complexity, cross-service consistency issues and tracing overhead.

## Decision
Use a **single Node.js 22 / Express 5 application** with explicit **routes → controllers → services → Mongoose models** layers and a MongoDB 7 datastore. REST/GraphQL/Socket.IO handlers call shared services so approval, notifications, and matching rules are centrally implemented. Keep the browser UI as static assets served by Express.

## Consequences

**Benefits:** one repository, easy debugging, shared authorization models, simple local deployment, lower operational cost, suitable for Labs 01–06.

**Tradeoffs:** a single backend is a single point of failure; Socket.IO's in-memory rooms are process-local; database and HTTP app scale together rather than independently. A highly available production service would need database replica sets, shared socket adapters and load balancing.

## Alternatives considered

1. **Microservices:** rejected: development and DevOps overhead exceeds this prototype's scale and deadline.
2. **Next.js frontend:** rejected: beyond Lab 06 and explicitly out of scope.
3. **Firebase-only backend:** rejected: would hide the Express/Mongoose authentication and architecture concepts required by the labs.

## Revision triggers
Reconsider if production traffic requires multiple independent deployments, distinct team ownership for services, or sustained throughput that a single Node process cannot handle. Revisit database transactions and availability before real campus adoption.
